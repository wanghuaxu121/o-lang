# O 语言 · 参考解释器 + C 后端

对应 [SPEC v0.6.1 / v0.7 类型系统](SPEC.md)。分两层：

1. **树遍历解释器** —— 可执行语义参考实现，把语言跑起来、盯住语义；
2. **C 后端**（`--emit-c` / `--cc`）—— 同一棵 AST 先做**类型标注**，再翻成 C，交给 `gcc -O2`。

## 用法

```bash
g++ -std=c++17 -O2 -Wall -Wextra -o olang olang.cpp     # 或 clang++
./olang --help                          全部开关（含可观察性三件套）

# 已经装到 PATH：/usr/local/bin/olang（包装脚本，转调本目录的 ./olang）
# 改了源码后重编：./run_tests.sh --fast   （或 clang++ -O2 -std=c++17 -o olang olang.cpp）
./olang examples/sms.o --mem-size 4096  临时把地址空间放大到 4096 个单元
./olang examples/demo.o --walias        显式地址区间重叠时给提示（默认静默，SPEC §12.4）

./olang examples/fib.o                  解释执行
./olang examples/sum.o --map            静态地址映射
./olang examples/types.o --cc           生成 C → gcc → 直接运行（一步式）
./olang examples/types.o --cc --rebuild 强制重编（默认复用没变过的 .gen.exe）
./olang examples/sum.o --map --json     地址映射（JSON，给工具吃）
./olang examples/sum.o --mem            退出时 dump 内存（带变量名）
./olang examples/sum.o --trace          逐条语句轨迹，打到 stderr
./olang examples/types.o --emit-c > t.c 只生成 C，自己编
gcc -std=c99 -O2 t.c -o t && ./t
```

`--cc` 等价于「`--emit-c` 写文件 + `gcc -std=c99 -O2 -w` + 运行」，
生成物 `程序.gen.exe` 会被缓存：源程序和 `olang` 二进制都没变过时直接复用（省掉 1.5–3 s 的 gcc），
`--rebuild` 或改过源文件才重编。
生成物是同目录的 `程序.gen.exe`（`.gen.c` 用完即删）。要调 gcc 参数就用 `--emit-c` 自己编。

## 地址空间大小

默认 **1024 个单元（8 KB）**。两种方式改，命令行优先：

```bash
./olang big.o --mem-size 8192      # 本次运行 / 本次生成
```

```o
#mem 8192                          // 写在源码里（必须在 O{} 之前）
```

上限 `1048576`（1M 单元 = 8 MB）。解释器、C 后端、`--map`、`--mem` 全都跟随同一个值 ——
`--emit-c` 生成的 `_mem[8192]` / `_sp = 8192` 就是它，所以两个后端的地址表仍然逐字节一致。

**为什么不做运行时可增长（vector 式）**：O 的地址是编译期常量，`--map` 是程序的静态产物，
栈从最高地址向下长。运行中途扩容会移动栈顶、让所有已分配的地址失效 —— 那等于换了一门语言。
`--mem-size` 是「启动时确定、运行期不变」，语义上就是「更大的静态数组」，
和「透明」是自洽的：**先声明要多大，然后一切可预测**。

## 可观察性：--map / --mem / --trace

「内存全透明」的三个观察口。它们和 `--emit-c` 用的是**同一套 layout**，
所以 `--map` 打印的地址就是生成 C 里 `_mem[...]` 的字面量。

### `--map` / `--map --json`

```bash
$ ./olang examples/sum.o --map
--- 静态地址映射 (MEM_SIZE=1024) ---
 addr  名字
    0  int      x10  size=10  a
   10  int      x1   size=1  i
   11  int      x1   size=1  s
 静态区结束 = 12, 栈从 1023 向下

$ ./olang examples/sum.o --map --json
{"mem_size":1024,"static_end":12,"stack_top":1023,"entries":[
  {"name":"a","type":"int","addr":0,"elems":10,"cells":10,"fence":[0,9]}, …]}
```

`--map` **只输出映射表、不执行程序**（要跑就别加这个开关）。
JSON 字段：`name / type / addr / elems / cells / fence`。

### `--mem` / `--mem=all`

退出时 dump 内存，每个单元标出属于哪个变量/字段：

```
--- 内存 dump（退出时）---
MEM_SIZE=1024  静态区 0..11  栈从 1023 向下  退出时 sp=1024
 addr  类型     值                     名字
    0  int      1                      a[0]
    9  int      10                     a[9]
   11  int      55                     s
（非零单元 12 / 1024；--mem=all 显示全部）
```

默认只列非零单元；`--mem=all` 打全部 1024 个。struct 会拆成 `p.x` / `p.y`。

### `--trace`

逐条语句打到 **stderr**：行号、语句类型、`sp`、以及这条语句写过的单元（新值）：

```
[     1] line 4    decl    sp=1024  writes: 0=0 1=0 2=0 … 9=0
[     2] line 7    decl    sp=1024  writes: 10=0
[     3] line 11   expr    sp=1024  writes: 0=1
```

stdout 仍只属于程序本身：`2>/dev/null` 只看结果，`1>/dev/null` 只看轨迹。

## 类型系统（v0.7）

| 类型 | 运行时表示 | 单元数 | 说明 |
|---|---|---|---|
| `bool` | int64 的 0/1 | 1 | 字面量 `true` / `false` |
| `int` | int64 | 1 | 32 位语义（写入截断） |
| `float` | double | 1 | 32 位精度（读写时舍入） |
| `double` | double | 1 | 64 位 IEEE |
| `char` | int64 | 1 | 输出当一个字节 |
| `struct` | 字段连续 | Σ字段 | 无填充；字段偏移 = 前序字段单元数之和 |
| `fn` | int64 下标 | 1 | 函数值 |

**关键设计：单元 = 64 位**，标量都占 1 个单元 → `sizeof(int)==1`，
**v0.6 的所有 int 程序语义零变化**，而 `double` 不必占两格。

- `T{x}` = 1 个 T；`T{x;y}` = `y-x+1` 个 T，占 `(y-x+1) * sizeof(T)` 个单元
- 结构体：`&{struct;Point} = {{double;x}, {double;y}}`，字段 `${p}.x`
- 显式转换：`${x}.as{double}`；提升：`bool → int → float → double`

## 导库与内置库（v0.8）

```o
#{"sys"}       // system
#{"file"}      // 文件 I/O

O{
    &{int;h} = {0}
    ${h} = open{"out.txt", "w"}
    puts{${h}, "hello\n"}
    close{${h}}
}
```

| 库 | 函数 |
|---|---|
| `sys` | `system{cmd}` → 退出码 |
| `file` | `open{path,mode}` `close{h}` `getc{h}` `putc{h,b}` `puts{h,s}` `eof{h}` `seek{h,p}` `tell{h}` `remove{path}` `exists{path}` `rename{a,b}` |

- 只能写在顶层（`O{}` 之前）；未知库、未导库就调用 → 编译错误
- `#` 管**代码依赖**，`@` 留给 `@config` / `@mmio` 这类**环境指令**
- `str` 从 v0.8 起是只读一等值：可作参数，也可 `&{str;p} = {"a.txt"}` 再传
- 文件是字节流，配合 `.{char; …}` 可以逐字节处理任意文件
- 两端都实现：解释器用 `FILE*` 数组，C 后端生成 64 项 `FILE*` 表 + `n_*` 辅助函数

## 类型标注（C 后端的前置）

解释器是动态的，不需要类型；C 后端必须知道每个表达式是 `.i` 还是 `.d`。
`--emit-c` 会先跑一遍标注 pass，给每个 `Expr` 标上静态类型：

| 表达式 | 标注结果 |
|---|---|
| 字面量 | `int` / `double` / `bool` |
| `${x}` | 变量类型；带下标 = 元素类型；带字段 = 字段类型；`.as{T}` = T |
| `${a}.size{}` | `int` |
| 调用 / 管道 | 函数声明的返回类型 |
| 算术 | 两侧提升（有 float/double → double） |
| 比较 / `&&` / `\|\|` / `~` | `bool` |
| 赋值 | 左值类型 |

顺带的好处：**未定义的变量/函数在生成 C 时就报错**，不必等运行时
（`olang.exe tests\err\e02_undef.o --emit-c` 直接报「第 3 行: 未定义的变量 'nope'」）。

## C 后端（`--emit-c`）

```c
typedef union { long long i; double d; } Cell;
static Cell _mem[1024];
static int _sp = 1024;

static int64_t o_fib(int64_t _p0) {
    int _sp0 = _sp; _sp -= 1; _mem[_sp + 0].i = (int64_t)(_p0);
    int64_t _ret = 0;
    if (...) { _ret = 1; goto _lend_fib; }
    { _ret = ...; goto _lend_fib; }
    _lend_fib: _sp = _sp0; return _ret;
}
```

- 静态变量 = 绝对单元号；函数局部 = `_sp + 帧内偏移`；`?{}` 用 `goto` 收尾以恢复 `_sp`
- 每个表达式按标注类型套 `(int32_t)` / `(double)`，与解释器的 32 位回绕和提升规则一致
- 函数签名按类型生成：返回 `int64_t`/`double`，参数同理，调用点按形参类型转换

**覆盖范围**：`int` / `bool` / `char` / `double` / `float` / `struct`（含结构体数组与字段）/
`str` 字面量与变量 / 命名函数（含递归）/ 循环 / 条件 / 数组 / 别名 /
**导库与内置库调用**（`sys` / `file`）。

**暂不支持**（明确报错，不静默生成错代码）：

| 特性 | 原因 | 计划 |
|---|---|---|
| 间接调用（`x \| ${f}`、函数值参数） | 需要按 (参数个数, 返回类型) 生成派发器 | v0.9 |
| 数组 / 结构体字面量初始化 | 需要元素级初始化语法 | v0.8 |
| 局部数组的 `.size{}` 之外的高阶用法 | — | 视需要 |

### fn 变量（两步写法）

```o
&{fn{int;int};h} = {}                     // ① 声明（{} = 全零，表示"还没有函数"）
${h} = o{{int;x}}{ ?{${x} + {1}} }        // ② 赋匿名函数
.{int; ${h}{5}}                           // ③ 间接调用 → 6
${h} = o{{int;x}}{ ?{${x} * {3}} }        // ④ 换一个 → 15
```

- `{}` 是**全零初始化**（对所有类型都合法）；`fn` 变量因此不能用 `{0}` 之类整数字面量初始化
- `&{fn{…};h} = o{…}{…}` 会被拒绝：那是"返回 fn 的函数"，语义有歧义

### v0.3 新增

| 特性 | 说明 |
|---|---|
| **`${f}{a, b}` 多参数间接调用** | 管道只能传 1 个，这个能传 N 个 |
| **struct 字面量** | `&{Point;p} = {1.5; 2.25}`（按字段声明顺序，缺省补 0） |
| **带签名的 `fn` 类型** | `{fn{int;int};g}`：参数个数/返回类型不符直接编译错误 |
| **静态检查两种模式都跑** | `annotateAll` 从 `--emit-c` 分支移到公共路径 |

### v0.2 三件收尾

| 特性 | 说明 |
|---|---|
| **引用参数** | `{int{0;63};&buf}`，调用写 `f{${x}}`，帧里只占 1 槽存地址 |
| **批量文件 I/O** | `read{h, ${buf}, {n}}` / `write{h, ${buf}, {n}}`（原生函数也支持引用参数） |
| **数组字面量** | `&{int;a} = {int{0;3}} = {10;20;30;40}`；元素不足补 0 |
| **C 后端支持匿名函数/间接调用** | 函数按 `o_f<下标>` 命名，`x \| ${f}` 生成派发链；`t05_apply` 现在双后端都跑 |
| **`#{"lib"}` 任意位置** | 顶层或 `O{}` 体内都可以写 |

### v0.2 新增：引用参数

```o
&{int;swap} = o{{int;&a}, {int;&b}}{      // & 在名字前 = 引用参数
    &{int;t} = {0}
    ${t} = ${a}
    ${a} = ${b}
    ${b} = ${t}
    ?{0}
}

&{int;fill} = o{{int{0;3};&buf}, {int;v}}{   // 引用一个 4 元素区段
    &{int;i} = {0}
    [${i} < ${buf}.size{}]{
        ${buf}{${i}} = ${v}
        ${i} = ${i} + {1}
    }
    ?{0}
}
```

- 调用写 `swap{${x}, ${y}}` —— 实参语法不变，由形参决定取地址还是取值
- 引用参数在帧里只占 1 个槽（存地址），不复制数据
- 区段长度在形参里声明（`{int{0;9};&buf}` = 10 个），实参更小会报错
- 传字面量给引用参数 → 报错「引用参数必须传变量」

> **为什么有「泄漏检查」这一组**：`TY_*` 是「种类」常量（从 100 起），类型表下标是 0..N，
> 两者混用会让 `gTypes.t[101]` 越界读。release 构建下 `vector::operator[]` 不检查，
> 症状是"恰好正确"；`-D_GLIBCXX_DEBUG` 会立刻 abort。这一组就是防止再次出现这类"运气通过"。

### 几个容易踩的点（已写进 SPEC）

| 规则 | 说明 |
|---|---|
| `char` | 值域 0..255，赋值时截断（`${c} = {300}` → 44），两端一致 |
| `str` | 只读；只能按**内容**比较 `==` / `!=`；`.as{数值}` 是错误 |
| `!` | 只能在循环内；不跨函数（顶层/跨函数都报错） |
| `.{T; e}` | 一次只输出一个值；`{x;y}` 形式报错（`{x;y}` 只用于输入） |

## 性能（fib(30)，交替 best-of-6）

| 实现 | 耗时 | 相对手写 C |
|---|---|---|
| 手写 C（`gcc -O2`） | 29.2 ms | 1.00× |
| **本项目的 C 后端** | **32.0 ms** | **1.10×** ✅ 满足 SPEC §15 的 ≤1.2× |
| 解释器 | ~13,600 ms | ~470× |

变量都住在 `_mem[]`（"内存透明"的代价），但 `gcc -O2` 能把 `_mem[_sp+k]` 提升进寄存器，所以几乎无损。

### arm64 Linux 实测（OPPO R11s / Ubuntu 24.04 PRoot，2026-10-25）

`fib(36)`（约 2400 万次调用，`gcc -O2`；本机进程启动开销 ≈ 96 ms）：

| 实现 | 墙钟 | 扣启动 | 每次调用 |
|---|---|---|---|
| 手写 C | 0.635 s | 0.56 s | ~3.1 ns |
| **本项目 C 后端** | **1.35 s** | **1.28 s** | **~6.6 ns** |
| 相对手写 C | — | — | **≈ 2.0×** |
| 解释器 | fib(30) 就要 60.4 s | — | 数百倍 |

两处 codegen 优化前，生成代码是 ~0.37 s@fib(36)（约 2.5×）；优化后 ~0.25 s@fib(36)（约 2.1×）。
剩下的一倍差距来自每次调用的固定开销：栈界检查分支、`int32↔int64` 反复转换、`_ret`/`goto` 结构。
要真正进 1.2× 需要做**类型定向的 codegen**（int 运算直接用 int32、尾位置直接 `return`），不是调参能解决的。

注意：`fib(30)` 这种规模的净计算只有 10–20 ms，会被 ~96 ms 的启动开销淹没，
墙钟比值看起来接近 1.1×，**评估 codegen 质量要用 fib(36) 这类吃满 CPU 的规模**。
这里的 2.5× 主要来自 `_mem` 单元模型：实参/局部都是 `Cell`，递归还要走 `_sp` 帧算术，
gcc 没法像手写 C 那样内联展开。

## 与 SPEC 的有意偏差

| 项 | SPEC | 实现 |
|---|---|---|
| 下标越界 | UB | 解释器运行时报错；生成 C 不检查 |
| 未定义变量/函数、实参个数、`!` 越界、`str` 转数值 | 编译错误 | **标注阶段报错，解释器与 C 后端一致（无输出、exit 2）** |
| 缺 `?{}` 返回值 | 编译错误 | 运行时（两种后端都是） |
| 结构体/数组字面量初始化 | 未定义 | 明确报错，只能零初始化后逐字段/逐元素赋值 |
| `int` 溢出 | UB（32 位） | 显式截断（可预测） |
